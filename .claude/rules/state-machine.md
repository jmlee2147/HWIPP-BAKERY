# 상태 머신 규칙

이 프로젝트에서 가장 먼저 완성하고 가장 많이 테스트해야 하는 영역입니다.
여기가 깨지면 관람객이 갇힙니다.

## 상태 이름과 명세서 화면의 대응

| 상태 | 명세서 화면 |
| --- | --- |
| `idle` | **시작 화면 (체험 시작)** |
| `target` | STEP.1 타겟 설정 |
| `questions` | STEP.2 데이터 입력 |
| `analyzing` | STEP.3 AI 분석 및 로딩 |
| `result` | STEP.4 결과 도출 |
| `share` | STEP.5 소장 및 확산 |

### `idle`은 대기 상태가 아니라 전시의 얼굴입니다

이름 때문에 놓치기 쉽지만, **전시 시간 중 가장 오래 떠 있는 화면**입니다.
관람객 1명당 체험이 2~3분이라면 그 사이 비어 있는 시간이 훨씬 깁니다.
지나가는 사람이 이 작품을 보는 순간의 대부분이 이 화면이므로, 관람객을 끌어당기는 역할을 합니다.

이 화면에만 걸린 것들:

- **전체화면 진입 전이라 주소창이 보일 수 있는 유일한 화면**입니다.
  주소창이 보이는 상태에서도 전시물로 보이도록 디자인합니다 (`.claude/rules/operations.md`).
- **자가 재시작이 일어나는 곳**입니다. 관람객이 없을 때만 리로드합니다.
- **에셋 프리로드가 도는 곳**입니다. 부팅 후 여기서 hot 계층을 전부 받습니다.

## 세션 스토어 (단일 소스)

```
SessionState {
  step:      'idle' | 'target' | 'questions' | 'analyzing' | 'result' | 'share'
  target:    TargetType | null          // STEP.1
  answers:   Partial<Answers>           // STEP.2 — 프리셋의 원천
  recipe:    Recipe | null              // STEP.4 결과
  resultId:  string | null              // STEP.5 QR용
  mode:      'create' | 'revise'        // 수정하기 재진입 여부
  startedAt: number                     // 유휴 타임아웃 기준
}
```

## "수정하기"는 뒤로가기가 아닙니다

기능명세서의 `결과 수정 (신규)`은 **STEP.2로 가되 이전 입력값이 프리셋되고,
완료 시 STEP.3부터 다시 진행**됩니다.

- **`answers`를 STEP.4 진입 시 비우지 않습니다.**
- `mode: 'revise'`로 STEP.2에 재진입하면 스토어의 `answers`가 그대로 폼 초기값이 됩니다.
- 별도 "이전 입력값" 캐시를 만들지 않습니다.

## 전이 규칙

| From | 이벤트 | To | 비고 |
| --- | --- | --- | --- |
| idle | 체험 시작 | target | 세션 신규 생성 |
| target | 수신자 선택 | questions | `mode='create'` |
| questions | 문답 완료 | analyzing | |
| analyzing | 분석 성공 | result | |
| analyzing | 분석 실패(재시도 후) | questions | **입력값 유지** |
| result | 소장/공유 | share | `resultId` 발급 |
| result | **수정하기** | questions | **`mode='revise'`, answers 유지** |
| share | **[처음으로] 버튼** | idle | 정상 종료 경로. 세션 전체 초기화 |
| *any* | 유휴 (STEP별 차등) | idle | 이탈 대비 |

## 세션 종료는 두 경로입니다

**(1) [처음으로] 버튼 — 주 경로**

STEP.5(소장·확산)에 명시적 CTA를 둡니다. 관람객이 스스로 누르거나 운영자가 다음 관람객을
위해 누릅니다. 누르면 즉시 세션 전체 초기화 → `idle`. **확인 다이얼로그를 넣지 않습니다.**

STEP.4에도 둘지는 검토 대상입니다 — 공유를 하지 않고 끝내는 관람객이 있습니다.

**(2) 유휴 타임아웃 — 이탈 대비**

STEP별로 차등합니다.

| STEP | 타임아웃 | 이유 |
| --- | --- | --- |
| target / questions | 60초 | 입력 중 이탈 |
| analyzing | **없음** | 분석이 끝날 때까지 타이머 정지 |
| result | 120초 | 결과를 읽는 시간 |
| **share (QR)** | **180초 이상** | **스캔하는 동안 화면이 사라지면 안 됩니다.** 휴대폰을 꺼내고 카메라를 켜는 시간이 필요합니다 |

타임아웃 직전 "계속하시겠어요?" 10초 카운트다운을 띄우고, 아무 입력이나 있으면 연장합니다.

## 세션 초기화 — 개인정보 사고 방지

리셋 후 이전 세션의 `answers`·`recipe`·`resultId`가 **완전히** 비워져야 합니다.
남아 있으면 다음 관람객이 남의 결과를 봅니다. 이것은 기능 버그가 아니라 개인정보 사고입니다.

타이머가 STEP 전환마다 정확히 리셋되는지, 리스너가 누적되지 않는지도 함께 확인합니다.

## STEP.2 문항 스키마

명세서에서 Q2·Q3은 취소선 처리(삭제)되어 **Q1, Q4, Q5, Q6 4문항**이 유효합니다.

| ID | 질문 | 수집 축 |
| --- | --- | --- |
| Q1 | 이 사람과 얼마나 자주 연락해요? | 친밀도·거리감 |
| Q4 | 선물 받는 분의 평소 스타일이나 성격은? | 디자인·컬러 톤 |
| Q5 | 오늘 이 케이크는 어떤 자리에서 쓰이나요? | TPO & 규모 |
| Q6 | 맛에 있어서 피해야 할 조건이 있나요? | 실용성·취향 제약 |

문항은 `features/questionnaire/schema.ts`에 **데이터로 선언**하고 UI는 스키마를 렌더링만 합니다.
