# Git 워크플로우

작업은 이슈 등록 → 작업 브랜치 → PR → `dev` 머지 순서로 진행합니다.

## 브랜치 구조

| 브랜치 | 용도 |
| --- | --- |
| `main` | 배포용. `dev`에서만 반영합니다 |
| `dev` | 통합용. 작업 브랜치의 PR 대상입니다 |
| 작업 브랜치 | 이슈 하나를 처리합니다. `dev`에서 만듭니다 |

- `main`과 `dev`에 직접 커밋하지 않습니다. 사용자가 명시적으로 이슈와 PR을 생략하자고 한 경우만 예외입니다.

## 1 이슈 = 1 PR

- 이슈 하나는 PR 하나로 끝나는 크기로 잡습니다. 커지면 이슈를 나눕니다.
- PR 하나에 여러 이슈를 섞지 않습니다.
- 작업 중 범위 밖의 일이 보이면 새 이슈로 등록하고 현재 PR에 넣지 않습니다.

## 순서

1. **이슈 등록**: `.github/ISSUE_TEMPLATE`의 형식을 따릅니다. 제목은 `[feat] ...`, `[fix] ...`, `[docs] ...`, `[chore] ...`처럼 type을 앞에 둡니다. 완료 조건을 체크리스트로 적습니다. 라벨은 커밋 type과 같은 이름(`feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`) 중 제목의 type과 같은 것을 하나 붙입니다.
2. **브랜치 생성**: 최신 `dev`에서 `<type>/<이슈번호>-<짧은-설명>` 이름으로 만듭니다. 예: `feat/3-experience-skeleton`
3. **작업과 커밋**: 작업 브랜치에서 `.claude/rules/commit-convention.md`에 맞춰 커밋합니다.
4. **검증**: `.claude/rules/verification.md` 기준으로 검증합니다. 실패한 채로 PR을 올리지 않습니다.
5. **PR 생성**: 사용자가 직접 확인하고 PR을 올리라고 한 뒤에 만듭니다. 대상은 `dev`입니다. 본문은 `.github/PULL_REQUEST_TEMPLATE.md`를 따르고 `Close #<이슈번호>`를 넣습니다. PR 제목은 `<type>: <subject>` 형식입니다.
6. **머지**: merge commit 방식으로 `dev`에 머지합니다. squash와 rebase는 쓰지 않습니다.
7. **정리**: 머지된 작업 브랜치는 삭제합니다.

## 이슈 자동 종료

기본 브랜치가 `main`이라 `dev`에 머지해도 `Close #번호`로 이슈가 자동으로 닫히지 않습니다. `dev` 머지 후 해당 이슈를 직접 닫습니다.

## 에이전트의 진행 범위

- 이슈 등록, 브랜치 생성, 작업 브랜치 커밋까지는 확인 없이 진행합니다.
- 작업을 마치면 푸시하거나 PR을 만들지 않고, 변경 내용과 검증 결과, 직접 확인하는 방법을 보고하고 멈춥니다.
- 푸시와 PR 생성은 사용자가 직접 확인한 뒤 PR을 올리라고 했을 때만 합니다.
- 이미 열린 PR의 브랜치에 추가 커밋을 푸시하는 것도 같은 기준을 따릅니다.
- `dev` 머지는 사용자가 직접 하거나 사용자가 지시했을 때만 합니다.
- `main` 반영, force push, 원격 브랜치 삭제, 히스토리 변경은 사용자가 지시했을 때만 합니다.
