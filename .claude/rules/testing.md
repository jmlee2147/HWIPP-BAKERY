# 테스트 규칙

전시물이고 기간이 짧습니다. **깨졌을 때 복구 불가능한 것만** 테스트합니다.

## 반드시 테스트합니다

| 대상 | 이유 |
| --- | --- |
| **세션 상태 머신 전이 전체** | 깨지면 관람객이 갇힙니다. 특히 **`revise` 재진입**(STEP.4→2, answers 유지, 완료 시 STEP.3부터) |
| **세션 초기화** | `[처음으로]`·유휴 리셋 후 이전 답변·결과가 **완전히** 비워지는가. 남으면 개인정보 사고입니다 |
| **유휴 타임아웃 STEP별 차등** | 특히 `analyzing`은 정지, `share`는 180초 이상 |
| **AI 폴백 경로** | API 실패·타임아웃·스키마 불일치일 때 각각 정상 결과가 나오는가 |
| **Zod 스키마 경계** | AI 응답이 enum 밖 값을 줬을 때 거부되고 폴백으로 가는가 |
| **매핑 테이블 → 에셋 경로** | 모든 조합이 존재하는 파일을 가리키는가 |

## 테스트하지 않습니다

모션, 레이아웃, 시각적 디테일. **눈으로 보는 게 더 빠르고 정확합니다.**
스냅샷 테스트는 만들지 않습니다 — 디자인이 자주 바뀌는 단계에서 유지 비용만 큽니다.

## 도구와 위치

- 단위/로직 테스트는 Vitest를 사용합니다.
- 테스트 파일은 대상 파일 옆에 둡니다. 유틸리티는 `.test.ts`, 컴포넌트는 `.test.tsx`.

## 작성 규칙

- 상태 머신은 **UI 없이** 순수 함수/스토어 단위로 테스트합니다. 렌더링을 끼우지 않습니다.
- AI 폴백은 실제 API를 호출하지 않습니다. 클라이언트를 주입 가능하게 만들고 실패를 주입합니다.
- 구현 세부사항을 그대로 복제하는 테스트를 피합니다.
- **`test.skip`·`.only`·빈 테스트는 머지 차단 사유입니다.** 미완성이면 실패하게 두는 게 낫습니다.
