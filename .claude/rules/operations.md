# 운영 규칙 — 관리가 필요 없어야 합니다

## 역할이 기준을 정합니다

| 역할 | 누구 | 전시 당일 |
| --- | --- | --- |
| 개발·설치 | 개발자 | **현장에 없을 수 있습니다** |
| 당일 운영 | **디자이너** (전시 참여자) | 부스에 있지만 자기 작품 응대로 바쁩니다 |

**현장에 있는 사람은 디버깅을 할 수 없습니다.** 능력이 아니라 역할의 문제입니다.

"꼬이면 새로고침하세요" 같은 지시는 성립하지 않습니다. 난이도를 떠나 **판단을 요구**하기 때문입니다 —
지금이 꼬인 건가 원래 느린 건가, 새로고침해도 되는 시점인가.

운영자가 부스에 있기는 합니다. **하지만 그건 안전망이지 설계 입력이 아닙니다.**
"사람이 고쳐주겠지"를 전제하면 고쳐야 하는 물건이 나옵니다.
**실사용자에게 그냥 열어놓아도 되는 수준**을 목표로 잡습니다.

## 전체화면 진입

webOS 브라우저는 키오스크 모드로 실행할 수 없습니다. 대신 **페이지가 직접 전체화면을 요청**합니다.

```
idle 화면 (주소창이 보일 수 있음)
  → 관람객이 [체험 시작] 탭       ← 사용자 제스처
  → requestFullscreen() 호출
  → 이후 세션 내내 전체화면 유지
```

- `requestFullscreen()`은 **사용자 제스처 없이는 호출할 수 없습니다.** 시작 버튼 탭에 묶습니다.
- 이미 전체화면이면 재호출하지 않습니다. `document.fullscreenElement`로 확인합니다.
- 전체화면이 해제되면(`fullscreenchange`) 다음 탭에서 다시 시도합니다.
- 자가 재시작 후에도 마찬가지로 첫 탭에서 재진입합니다.
- **미지원이어도 앱이 깨지지 않아야 합니다.** 실패는 무시하고 그대로 진행합니다.

idle 화면은 주소창이 보이는 상태에서도 전시물로 보이도록 디자인해 두는 것이 안전합니다.

## 절차가 아니라 설계로 풉니다

| 절차로 넘기기 쉬운 것 | 설계로 |
| --- | --- |
| 매일 브라우저 열기 | **애초에 닫지 않습니다.** TV 자동 꺼짐·절전을 끄고 AC 상시 연결 |
| 꼬이면 새로고침 | 에러 바운더리가 `idle`로 자동 복귀 + 유휴 타임아웃이 항상 살아 있음 |
| 프리로드를 눈으로 확인 | 실패 시 지수 백오프 자동 재시도 |
| 한 시간에 한 번 새로고침 | **스스로 새로고침합니다** (아래) |
| 네트워크 복구를 사람이 확인 | `online` 이벤트 감지 → 자동 재시도 |

리뷰에서 "운영 절차로 안내하면 된다"는 결론이 나오면 그건 대부분 **설계 미완성**입니다.

## 자가 복구

| 상황 | 자동 처리 |
| --- | --- |
| 런타임 에러 | 에러 바운더리 → **`idle` 자동 복귀.** 에러 화면을 절대 노출하지 않습니다 |
| 세션 꼬임 | 유휴 타임아웃이 모든 STEP에서 살아 있으므로 **반드시 `idle`로 돌아옵니다** |
| **메모리 누적** | 아래 자가 재시작 |
| 에셋 프리로드 실패 | 지수 백오프 무기한 재시도, 실패한 항목만 |
| 네트워크 끊김 | 서비스워커 캐시로 계속 동작 + `online` 이벤트 자동 재시도 |
| AI 호출 실패 | 결정적 매핑 테이블 폴백. 관람객은 모릅니다 |
| 브라우저 종료 | 닫을 일이 없습니다 |

**자가 재시작 조건** — 모두 만족할 때만 실행합니다. 하나라도 빠지면 관람객 화면을 끊습니다.

```
step === 'idle'  ∧  무입력 N초 경과  ∧  ( 가동 시간 > 2시간  ∨  배포 버전 불일치 )
→ location.reload()
```

서비스워커 캐시가 있어 리로드는 거의 즉시 끝나고, 관람객이 없는 시점이므로 아무도 보지 못합니다.
**이것은 메모리 누수의 해결책이 아니라 안전망입니다** — 누수 자체는 없애고,
그럼에도 남는 잔여 증가를 이걸로 텁니다.

## 배포가 키오스크에 반영되지 않는 문제

브라우저가 계속 켜져 있고 서비스워커가 에셋을 캐시합니다.
**긴급 수정을 배포해도 화면은 옛날 버전 그대로입니다.** 전시 중에 고칠 수 없다는 뜻입니다.

하트비트를 재사용해 해결합니다:

```
키오스크 → POST /api/heartbeat  (60초마다)
서버     → { deployedVersion: "abc123" } 응답
키오스크 → 자기 빌드 버전과 다르면 → 다음 idle에서 자가 재시작
         → 서비스워커가 새 버전 캐시로 교체
```

버전 불일치는 2시간 대기를 기다리지 않습니다.
배포가 반영됐는지는 하트비트에 실려 오는 클라이언트 버전으로 확인합니다.

## 원격 모니터링 — 디자이너 대신 개발자가 압니다

감시를 디자이너에게 시킬 수 없습니다. 대신 개발자가 원격으로 압니다.

| 수단 | 구현 | 목적 |
| --- | --- | --- |
| **하트비트** | 60초마다 `POST /api/heartbeat` | 끊기면 화면이 죽은 것입니다 |
| **클라이언트 에러 리포팅** | 에러 바운더리 → `POST /api/log` | webOS엔 개발자도구가 없습니다. **유일한 창입니다** |
| **폴백 카운터** | AI 폴백이 탈 때마다 서버 로그 | 반복되면 네트워크·API 문제 |
| **알림** | Vercel Cron 5분마다 `lastSeen` 확인 → 초과 시 알림 | 6시에 아는 것과 10시 5분에 아는 것의 차이 |

이 넷이면 충분합니다. Sentry·대시보드·APM은 이 규모에 과합니다.
**목표는 관측이지 관제가 아닙니다.**

## 관리자 대시보드를 만들지 않습니다

검토했으나 **근거가 없어 뺐습니다.** 다시 제안이 올라오면 이 표로 반박합니다.

| 두려던 것 | 뺀 이유 |
| --- | --- |
| 현재 세션 상태 | 운영자가 27" 화면을 직접 보고 있습니다 |
| 누적 세션 수 | 결과 레코드가 KV에 쌓입니다. 전시 후에 셉니다 |
| 에러 로그 | `/api/*` 실패는 Vercel 로그에 남습니다 |
| 프리로드 상태 | 부팅 화면 진행률로 충분합니다 |
| 강제 리셋 | `[처음으로]` 버튼 + 유휴 타임아웃 + 에러 자동 복귀가 이미 처리합니다 |

**관리 화면이 필요하다는 것은 대개 자가 복구가 부족하다는 신호입니다.**

예외로 `/debug` 한 장만 둡니다. 대시보드가 아니라 **설치 시 1회용 하드웨어 확인 페이지**입니다.
뷰포트·DPR·UA와 **`requestFullscreen()`이 실제로 브라우저 UI를 숨기는지**를 한 화면에 찍습니다.
기능 지원 여부(서비스워커·AVIF 등)는 Chromium 108 기준으로 이미 확정되어 확인할 필요가 없습니다.
필요한 이유는 하나 — **webOS 브라우저에는 개발자도구가 없어** 리모컨으로 콘솔을 열 수 없습니다.

## 로그 규약

- 구조화 로그(JSON). `console.log("에러남")` 같은 건 쓸모가 없습니다.
- 모든 로그에 `sessionId`를 넣습니다 — 한 관람객의 경로를 따라갈 수 있어야 합니다.
- 레벨: `error`(개입 필요) / `warn`(폴백 발동 등 추적 대상) / `info`(세션 시작·완료)
- **개인정보를 로그에 넣지 않습니다.**

## 에러 처리 계층 — 아래로 갈수록 조용해집니다

| 계층 | 정책 |
| --- | --- |
| `lib/*` 순수 로직 | 던집니다. 여기서 삼키지 않습니다 |
| `/api/*` 라우트 | 잡아서 구조화 로그 + 적절한 상태코드. 스택트레이스를 응답에 넣지 않습니다 |
| 데이터 페칭 훅 | 잡아서 폴백 데이터 반환. 호출부는 에러를 모릅니다 |
| 화면 컴포넌트 | **에러 UI를 만들지 않습니다** |
| 에러 바운더리 | 최후 방어. 로그 전송 후 **`idle` 자동 복귀** |

**금지**: 빈 `catch {}`, `catch` 후 `console.log`만 하고 넘어가기, 에러 메시지를 관람객 화면에 노출.

## 설치 시 1회 기기 설정

반복되는 관리가 아니라 설치 시점의 기기 설정입니다. 케이블 연결과 같은 범주입니다.

| 항목 | 조치 |
| --- | --- |
| **무입력 자동 꺼짐** | 끕니다. TV는 통상 4시간 무입력이면 스스로 꺼집니다 |
| 화면 절전 · 자동 밝기 | 끕니다. 자동 밝기는 케이크 색 표현을 망칩니다 |
| 화면 보호기 · 무드메이커 | 끕니다 |
| **전원** | **AC 상시 연결** |
| 소프트웨어 자동 업데이트 | 끕니다 |
| 화면 회전 | 세로 고정 (로테이팅 ±90) |
| 와이파이 | 고정 SSID. 캡티브 포털·기기 수 제한을 사전 확인합니다 |
| 브라우저 | 배포 URL을 열고 **그대로 둡니다.** 이후 닫지 않습니다 |
| 즐겨찾기 | **1번 칸**에 배포 URL 등록 — 리모컨 입력을 최소화합니다 |

## 인수인계 — 두 줄을 넘으면 안 됩니다

```
정상:   아무것도 하지 않습니다
이상 시: TV를 껐다 켜고 즐겨찾기 1번을 누릅니다
```

**이게 전부여야 합니다.** 항목이 하나라도 늘어난다면 자가 복구가 부족하다는 신호이지,
인수인계 문서를 길게 쓸 이유가 아닙니다. 개발자 연락처를 부스에 붙여둡니다.

## 출시 기준

"기능이 동작한다"가 아니라 **"사람 없이 하루를 버틴다"**가 완료 조건입니다.

- [ ] 8시간 연속 구동에서 메모리 우상향 없음, 프레임 드랍 악화 없음
- [ ] 네트워크를 끊어도 체험이 끝까지 돌아감 (AI만 폴백)
- [ ] 고의로 런타임 에러를 발생시켜도 `idle`로 자동 복귀. 에러 화면이 절대 안 보임
- [ ] API 키를 잘못된 값으로 바꿔도 관람객 경험이 동일함 (폴백)
- [ ] 모든 STEP에서 유휴 타임아웃 동작. share는 180초 이상 확인
- [ ] `[처음으로]` 버튼이 세션을 완전히 초기화함 — 이전 답변·결과가 남지 않음
- [ ] 자가 재시작이 `idle`에서만 동작하고 관람객 화면을 끊지 않음
- [ ] 배포 후 키오스크가 **스스로** 새 버전으로 갱신됨
- [ ] `/api/analyze`에 rate limit·일일 상한이 걸려 있음
- [ ] 하트비트·에러 리포팅이 실제로 도착함
- [ ] 디자이너 인수인계가 두 줄을 넘지 않음

**남은 항목이 있으면 개발이 안 끝난 것입니다.** 전시장에서 메꾸지 않습니다.

## 장시간 구동 테스트

오픈 전에 **최소 8시간 연속 구동**을 돌리고 세션을 자동 반복시킵니다.

- heap snapshot을 주기적으로 떠 우상향 추세가 있는지 봅니다
- 프레임 드랍이 시간에 따라 악화되는지 봅니다
- 브라우저가 스스로 죽는지 봅니다

**반드시 스탠바이미2 실물에서** 합니다. 개발 맥에서 8시간 돌린 결과는 TV SoC의 메모리 거동을
대변하지 못합니다. 자가 재시작은 안전망이지 누수를 방치해도 된다는 뜻이 아닙니다 —
2시간 안에 체감될 만큼 새면 관람객 앞에서 버벅입니다.
