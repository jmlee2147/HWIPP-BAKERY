# 커밋 컨벤션

커밋 메시지는 Udacity Git Style Guide를 기반으로, 변경 목적을 빠르게 파악할 수 있게 작성합니다.

## 커밋 시점

- 이슈에 연결된 작업 브랜치에서는 작업 단위로 커밋합니다 (`.claude/rules/git-workflow.md`).
- `main`과 `dev`에는 직접 커밋하지 않습니다. 사용자가 명시적으로 요청한 경우만 예외입니다.
- 이슈 없이 진행한 작업은 사용자가 "커밋하자", "커밋해줘"처럼 요청했을 때만 커밋합니다.
- `git reset`, `git revert`, force push 같은 히스토리 변경은 사용자가 지시했을 때만 합니다.

## 형식

```text
<type>: <subject>
```

scope는 기본적으로 사용하지 않습니다. 여러 목적이 섞이면 커밋을 분리합니다.

## Type

| Type | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서, 주석, README, AI 지침 변경 |
| `style` | 포맷팅처럼 동작 영향 없는 변경 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가/수정 |
| `chore` | 설정, 빌드, 의존성, 보조 작업 |

## Subject

- 한국어 명령형 또는 명사형으로 짧게 작성합니다.
- 50자 이내를 우선합니다.
- 무엇을 했는지보다 왜 변경했는지가 드러나게 씁니다.
- 파일명 나열로 subject를 채우지 않습니다.
- 마침표를 붙이지 않습니다.

## 예시

```text
docs: AI 작업 지침 정리
chore: 프로젝트 초기 설정 추가
feat: 수신인 관계 카드 뒤집기 추가
fix: 키오스크에서 스테이지가 잘리는 문제 수정
test: 스테이지 스케일 계산 테스트 추가
```

## 금지

- 커밋 메시지에 이모지를 넣지 않습니다.
- `Generated by`, `Co-Authored-By` 같은 AI 출처 문구를 넣지 않습니다.
- 검증하지 않은 변경을 검증한 것처럼 쓰지 않습니다.
- 서로 독립적인 기능과 설정 변경을 한 커밋에 섞지 않습니다.
