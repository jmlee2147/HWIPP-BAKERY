# 커밋 컨벤션

## 먼저: 커밋은 요청받았을 때만 합니다

**사용자가 커밋하라고 하기 전에 커밋하지 않습니다.** 작업 요청은 커밋 요청이 아닙니다.

- "컴포넌트 세팅 들어가자", "폰트부터 하자" → **작업만** 하고 멈춥니다
- "커밋하자", "커밋해줘" → 그때 커밋합니다
- 작업이 끝나면 변경 내용을 보고하고, 커밋 여부는 사용자가 정합니다
- 한 번 커밋을 취소당했다면 그 뒤로는 더더욱 임의 커밋하지 않습니다

`git reset`, `git revert` 같은 히스토리 변경, 그리고 `git push` 도 요청받았을 때만 합니다.

**GitHub 이슈와 마일스톤은 만들지 않습니다.** 사용자가 직접 관리합니다.
할 일이 보이면 이슈로 만들지 말고 대화에서 알립니다.

---

## 브랜치 전략

```
feat/*  →  dev  →  main
                    ↑
              hotfix/*  (전시 중 긴급 수정만)
```

| 브랜치 | 역할 | 배포 |
| --- | --- | --- |
| `main` | 전시에 실제로 쓰이는 것. 항상 동작해야 한다 | Vercel production |
| `dev` | 통합 브랜치. 기능이 모이는 곳 | Vercel preview |
| `feat/*` | 개별 작업 | PR 프리뷰 |

`dev` 를 두는 이유는 **전시 기간 중 `main` 을 동결**해야 하기 때문입니다.
그 기간에도 작업은 계속되므로 받아줄 곳이 필요합니다.
또 스탠바이미2를 `dev` 프리뷰 URL에 물려 실기 테스트한 뒤 `main` 으로 올릴 수 있습니다.

### 이름

커밋 `<type>` 과 같은 말을 씁니다.

```
feat/common-components     공용 컴포넌트 5종
feat/state-machine         상태 머신
fix/share-timeout          공유 화면 타임아웃
hotfix/qr-timeout          전시 중 긴급 수정
chore/ci                   CI 설정
docs/operations            운영 문서
```

- 소문자와 하이픈만 씁니다. 한글·공백을 쓰지 않습니다.
- 이슈 번호가 있으면 뒤에 붙입니다: `feat/state-machine-12`

### 흐름

1. `dev` 를 최신으로 맞추고 `feat/*` 를 땁니다.
2. 작업하고 커밋합니다 (커밋은 요청받았을 때만 — 위 참조).
3. `dev` 로 PR을 올립니다. CI 게이트를 통과해야 머지할 수 있습니다.
4. 머지 후 브랜치를 지웁니다.
5. `dev` 가 검증되면 `main` 으로 PR을 올려 배포합니다.

### 규칙

- **`main` 과 `dev` 에 직접 커밋하지 않습니다.** 프로젝트 초기 세팅만 예외였습니다.
- 브랜치 하나에 목적 하나. 공용 컴포넌트와 상태 머신을 한 브랜치에서 하지 않습니다.
- 브랜치를 오래 끌지 않습니다. 길어지면 벌어져서 충돌이 커집니다.
- **전시 기간 중에는 `main` 을 동결합니다.** 긴급 수정만 `hotfix/*` 로 `main` 에 넣고,
  같은 내용을 `dev` 로 백머지합니다. 반영은 버전 전파 경로를 탑니다
  (`.claude/rules/operations.md`).

---

커밋 메시지는 Udacity Git Style Guide를 기반으로, 변경 목적을 빠르게 파악할 수 있게 작성합니다.

## 형식

```text
<type>: <subject>
```

scope는 기본적으로 사용하지 않습니다. 여러 목적이 섞이면 커밋을 분리합니다.

## Type

| Type | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서, 주석, README, AI 지침 변경 |
| `style` | 포맷팅처럼 동작 영향 없는 변경 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가/수정 |
| `chore` | 설정, 빌드, 의존성, 보조 작업 |

## Subject

- 한국어 명령형 또는 명사형으로 짧게 작성합니다.
- 50자 이내를 우선합니다.
- 무엇을 했는지보다 왜 변경했는지가 드러나게 씁니다.
- 파일명 나열로 subject를 채우지 않습니다.
- 마침표를 붙이지 않습니다.

## 예시

```text
docs: AI 작업 지침 정리
chore: 프로젝트 초기 설정 추가
feat: 멤버 목록 API 연결
fix: 폼 파일 전송 오류 수정
test: 목록 empty 상태 테스트 추가
```

## 금지

- `Generated by`, `Co-Authored-By` 같은 AI 출처 문구를 넣지 않습니다.
- 이모지를 넣지 않습니다.
- 검증하지 않은 변경을 검증한 것처럼 쓰지 않습니다.
- 서로 독립적인 기능과 설정 변경을 한 커밋에 섞지 않습니다.
