# 에셋 규칙

이미지가 매우 많고 해상도가 높습니다. 전시에서 "이미지가 늦게 뜨는" 것은 치명적입니다.

## 일반 웹 상식이 여기서 틀리는 지점

고정 해상도 단일 기기입니다. 반응형이 없고 디바이스 픽셀 비율도 하나입니다.

- **배수 에셋을 여러 개 만들지 않습니다.** 최종 출력 크기 하나만 준비합니다.
- **`next/image`를 쓰지 않습니다.** 정적 `<img>` + 프리로드가 더 빠릅니다.
  로컬 고정 에셋이라 런타임 리사이즈·포맷 협상은 이득 없이 첫 표시만 늦춥니다.
- **`srcset`·`sizes`를 쓰지 않습니다.** 고를 후보가 하나뿐입니다.

## 가장 중요한 숫자: 디코딩 메모리

**파일 크기와 메모리 사용량은 다릅니다.** 브라우저가 이미지를 그리려면 압축을 풀어 비트맵으로
들고 있어야 하고, 그 크기는 압축률과 **무관하게** 픽셀 수로 결정됩니다.

```
풀스크린 1장 = 1440 × 2560 × 4바이트(RGBA) ≈ 14 MB (RAM)   ← 출력 픽셀 기준
```

500KB짜리 파일도 화면에 떠 있는 동안은 14MB를 씁니다.
"파일 총합 20MB니까 괜찮다"는 판단은 틀렸습니다 — 풀스크린 40장이면 **약 560MB**입니다.
**파일 크기만 보고 예산을 승인하지 않습니다.**

## 예산 (CI에서 강제)

```
동시 상주 디코딩 ≤ 300MB   ·   파일 총합 ≤ 300MB   ·   Lottie ≤ 20MB
```

- TV SoC는 RAM을 OS와 공유하므로 데스크톱 브라우저처럼 여유롭게 쓸 수 없습니다.
- 풀스크린 1장이 14MB이므로 **hot 계층은 사실상 20장 남짓**이 상한입니다.
- 디코딩 예산은 파일 크기가 아니라 **hot 계층 에셋의 픽셀 총량 × 4바이트**로 계산합니다.
- **초과하면 빌드를 실패시킵니다.** 코드로 우회하지 않습니다 — 디자인 단계에서 해결할 문제입니다.

## 포맷·명명

- **AVIF.** Chromium 108이 지원합니다(Chrome 85+). WebP 대비 용량 40~50% 절감.
  단 **디코딩 메모리는 포맷과 무관**합니다 — 줄어드는 것은 전송·저장 용량뿐입니다.
- **에셋은 캔버스 좌표(1080)가 아니라 최종 출력 픽셀(1440) 기준으로 뽑습니다.**
  Figma 익스포트 **2x**를 씁니다 — 1x면 1.33배 확대되어 뿌옇고, 2x는 브라우저가 축소하므로 손실이 없습니다.
- 변형이 많은 이미지는 **파일명을 매핑 키와 일치**시킵니다: `cake_{design}_{color}.avif`.
  코드에서 조건 분기 대신 경로 조합으로 해결되게 합니다.
  조건 분기 테이블을 만들고 있다면 명명이 틀린 것입니다.
- 원본은 저장소에 커밋하지 않습니다. 변환 산출물만 `public/`에 둡니다.

## Figma 에셋은 받은 직후 정리합니다

Figma MCP는 **캔버스의 노드 그룹마다 파일을 하나씩** 내보냅니다. 그래서 같은 도형이 인스턴스
수만큼 복제되고, 장식 하나가 여러 조각으로 쪼개져 나옵니다. 그대로 두면 파일 수와 `<img>` 태그가
불어납니다.

대화 박스 하나에서 18개가 나왔고 정리 후 4개가 됐습니다(76KB → 28KB).
케이크 부품은 섹션이 16개라 훨씬 크게 벌어집니다.

### 1. 중복 제거

id, 그라디언트 참조, 소수점 오차를 정규화한 뒤 해시를 비교합니다.
Figma는 인스턴스마다 좌표를 0.01px 단위로 다르게 내보내고 그라디언트 id에 일련번호를 붙이므로,
**바이트 비교로도 id만 지운 비교로도 안 잡힙니다.**

```bash
for f in *.svg; do
  printf "%-20s %s\n" "$f" "$(sed -E '
    s/id="[^"]*"//g;
    s/url\(#[^)]*\)/url(#G)/g;
    s/[0-9]+\.[0-9]{2,}/N/g
  ' "$f" | md5 -q)"
done | sort -k2
```

`url(#...)` 정규화를 빠뜨려 실제로 중복을 놓친 적이 있습니다(`progress-label-5`).

해시가 같으면 **파일 하나만 남기고 위치 배열로 반복**합니다.

```tsx
const CREAM: Box[] = [ /* 위치 11개 */ ]
{CREAM.map((box) => <Layer src="/img/dialog/cream.svg" box={box} />)}
```

### 2. 같은 영역의 조각은 병합

한 영역을 덮는 장식이 여러 조각으로 나왔다면 하나의 SVG로 합칩니다.
각 조각을 부모 기준 오프셋만큼 `translate` 해서 붙이면 결과는 동일합니다.
합칠 때 `id` 를 제거해야 충돌하지 않습니다.

### 3. 보고

정리 전/후 **파일 개수와 용량**을 보고합니다. 정리하지 않은 채로 매니페스트에 넣지 않습니다.

## 매니페스트는 자동 생성합니다

`lib/assets/manifest.ts`를 **수기로 관리하지 않습니다.**
`public/img`·`public/lottie` 스캔으로 빌드 타임에 생성합니다.
사람이 목록을 유지하면 반드시 빠지고, 전시 중에 빠진 것이 드러납니다.

생성 시 함께 검증합니다:

- 예산 초과 여부 (위)
- **매핑 테이블(`lib/mapping`)이 참조하는 모든 키에 대응 파일이 실제로 존재하는지.**
  여기서 잡지 못하면 전시 중 깨진 이미지가 됩니다.
- 각 에셋의 계층(hot/warm/cold)이 매니페스트에 **선언**되어 있는지. 코드에 흩어놓지 않습니다.

## 캐싱·프리로딩은 두 층입니다

**1층 — 서비스워커 프리캐싱 (디스크)**

앱 셸·이미지·Lottie·폰트를 PWA 캐시에 넣습니다. 에셋은 `cache-first`, API는 `network-only` + 폴백.
캐시 이름에 빌드 해시를 넣어 버전이 섞이지 않게 합니다.

목적은 **단절 대비가 아니라 재다운로드 방지**입니다 — 새로고침마다 수백 MB를 다시 받으면
혼잡한 전시장 와이파이에서 체감이 나빠집니다. 네트워크가 끊겨도 체험이 도는 것은 부수 효과입니다.

매니페스트가 프리캐시 목록의 단일 출처입니다. 별도 목록을 만들지 않습니다.

**2층 — 런타임 메모리 프리로드**

디스크에 있어도 디코딩은 매번 일어납니다.

| 계층 | 대상 | 정책 |
| --- | --- | --- |
| **hot** | UI·배경·공통 요소·Lottie | 부팅 시 1회 로드 후 **해제하지 않음** |
| **warm** | STEP.1 선택으로 좁혀진 결과 이미지 후보군 | STEP.1 직후 프리페치, 세션 종료 시 해제 |
| **cold** | 나머지 변형 전체 | 필요 시 로드. 디코딩 예산의 완충재 |

STEP.1에서 타겟을 고르는 순간 후보군이 크게 줄어듭니다 — 여기가 warm 프리페치의 최적 타이밍입니다.
프리로드 실패는 **지수 백오프로 자동 재시도**합니다. 사람이 확인할 일이 아닙니다.

## 메모리 정책 (모션과 정반대라 헷갈립니다)

- **hot 이미지: 해제하지 않습니다.** 의도적으로 상주시키고 총량은 예산으로 상한 관리합니다.
- **warm 이미지: 세션 종료 시 참조를 끊습니다.**
- **Lottie: 반드시 해제합니다.** (`.claude/rules/motion.md`)

이 비대칭을 코드 주석으로 명시합니다. 나중에 누군가 "일관성" 이름으로 hot 이미지를 해제하려 듭니다.

## 결과 이미지 생성 (STEP.5)

- 화면 캡처(html2canvas)가 아닌 **서버 렌더(Satori + resvg)** → 폰트·레이아웃이 기기와 무관하게 결정적입니다.
- 출력 **1080×1920 PNG** (인스타 스토리 비율) — 디자인 캔버스와 같은 크기라 추가 변환이 없습니다.
- `/api/og/[resultId]`가 요청 시 렌더 후 캐시합니다. 키오스크는 QR만 그립니다.

## 작업 절차

1. 에셋 추가·변경 시 매니페스트를 재생성하고 **예산 수치를 변경 전/후로 보고**합니다.
2. 변환 스크립트는 멱등해야 합니다. 재실행이 같은 결과를 내야 합니다.
3. 매핑 키 ↔ 파일 교차 검증을 돌리고 결과를 보고합니다.
