# 작업 규칙

코드 품질 원칙, 작업 흐름, 검증 기준을 한곳에 둡니다. Tier 1이라 항상 함께 로드됩니다.

---

## 코드 품질

이 문서는 LLM 코딩에서 흔한 실수를 줄이기 위한 기본 행동 규칙입니다. 빠른 진행보다 정확성, 단순성, 검증 가능성을 우선합니다.

### 1. 코드 작성 전에 생각하기

추측하지 말고, 모호함을 숨기지 말고, 구현 전에 가정과 트레이드오프를 드러냅니다.

- 가정을 명시합니다.
- 해석이 여러 개라면 가능한 해석을 말합니다.
- 더 단순한 접근이 있다면 설명합니다.
- 모호함이 해결 방향을 바꿀 정도라면 수정 전에 질문합니다.

### 2. 단순함 우선

문제를 해결하는 최소한의 코드만 작성합니다.

- 요청하지 않은 기능을 추가하지 않습니다.
- 한 번만 쓰는 코드를 위한 추상화를 만들지 않습니다.
- 요청하지 않은 설정 가능성이나 확장성을 넣지 않습니다.
- 해결책이 문제보다 커졌다면 단순화합니다.

### 3. 필요한 부분만 수정

요청을 해결하는 데 필요한 파일과 줄만 수정합니다.

- 필요한 경우가 아니면 주변 코드를 리팩터링하지 않습니다.
- 기존 스타일, 네이밍, 파일 위치를 따릅니다.
- 이번 변경으로 unused가 된 import, 변수, 함수는 정리합니다.
- 관련 없는 dead code는 삭제하지 말고 언급만 합니다.

### 4. 목표 기반 실행

작업을 검증 가능한 목표로 바꿉니다. `동작하게 만들기`처럼 약한 목표 대신 단계마다 명확한 성공 기준을 답니다.

### 5. 데이터로 선언하고 UI는 렌더링만

문항, 매핑 테이블, 에셋 매니페스트, 모션 토큰은 **데이터로 선언**합니다.
UI 컴포넌트는 그 데이터를 렌더링만 합니다.

전시 직전에 문항이나 에셋이 바뀌어도 컴포넌트를 건드리지 않기 위한 규칙입니다.
UI 코드에 조건 분기 테이블이 생기고 있다면 데이터 설계가 틀린 것입니다.

### 6. 성능 주장은 수치로

이 프로젝트는 TV SoC에서 돌아갑니다. 개발 맥에서 잘 도는 것은 근거가 아닙니다.

- "부드럽게 동작합니다", "누수 없어 보입니다" 같은 서술은 근거로 인정하지 않습니다.
- 측정 방법과 조건(스로틀 배율, 측정 구간, 시간축)을 함께 보고합니다.
- 자세한 기준은 아래 **검증** 절을 따릅니다.

### 7. 주석은 결론만 쓴다

배경·대안·검토 과정을 주석에 늘어놓지 않습니다. **판단의 결론과, 필요하면 근거 한 줄**이면 충분합니다.

- 근거가 길면 `.claude/rules/` 나 `docs/decisions/` 에 쓰고 주석에서는 경로만 가리킵니다.
- 코드를 읽으면 알 수 있는 내용을 반복하지 않습니다.
- 함수 위 문서 주석도 3~4줄을 넘기지 않습니다.

```ts
// 좋음
/** 캔버스를 뷰포트에 맞추는 배율. 상수로 박지 않는다 — webOS 뷰포트 미확인. */

// 나쁨: 배경 설명을 주석이 떠안고 있다
/**
 * Figma 아트보드는 세로 1080×1920, 표시 패널은 세로 1440×2560.
 * 둘 다 9:16이라 레이아웃이 재배치될 일이 없으므로 반응형을 만들지 않고
 * 캔버스를 통째로 scale 한다. 세로만 기준으로 하면 가로가 넘치는데 ...
 */
```

### 8. 이모지를 쓰지 않는다

주석, 문서, 커밋 메시지, 로그 어디에도 이모지를 쓰지 않습니다.
강조가 필요하면 `**굵게**` 또는 `주의:` 같은 말로 씁니다.

- 예외: 화면에 실제로 렌더링되는 디자인 요소 (예: 진행률 바 노브의 `♥`)
- `→` `←` `↔` 같은 화살표는 플로우 표기이므로 이모지로 보지 않습니다

### 9. 가짜 완료 금지

- `TODO` 주석, `test.skip`, `.only`, 빈 테스트, 미구현 분기는 완료 근거가 아닙니다.
- 구현하거나, 막힌 지점을 명시적으로 보고합니다.
- 전시장에서 메꾸는 것을 전제한 "거의 다 됨"은 완료가 아닙니다.

## 작업 흐름

### 기본 흐름

1. 현재 구현과 관련 지침을 확인합니다.
2. 가장 작은 검증 가능한 성공 기준을 정의합니다.
3. 작업에 필요한 파일만 수정합니다.
4. 가장 구체적이고 유효한 검증을 실행합니다.
5. 결과, 근거, 남은 공백을 보고합니다.

### 구현 순서

이 프로젝트는 순서를 지키는 것이 특히 중요합니다.

| # | 단계 | 완료 기준 |
| --- | --- | --- |
| 1 | 골격 | Next.js + TS + Tailwind v3, 고정 캔버스 스케일러, 디자인 토큰 |
| 2 | **상태 머신** | 5-STEP 전이 + `revise` 재진입 + `[처음으로]` + STEP별 유휴 리셋이 **모션 없이** 동작 |
| 3 | 문답 스키마 | Q1/Q4/Q5/Q6 데이터 선언 + 프리셋 재진입 검증 |
| 4 | AI 파이프라인 | `/api/analyze` + Zod 스키마 + 폴백 + 공개 API 보호 |
| 5 | 에셋 파이프라인 | 매니페스트 자동 생성 + 프리캐싱 + 예산 검증 |
| 6 | 모션 레이어 | `StepTransition`·`LottieStage` 적용, 스로틀 조건에서 60fps 계측 |
| 7 | 결과 이미지·QR | Satori 렌더 + `/r/[id]` 모바일 페이지 |
| 8 | 자가 복구·모니터링 | 에러 자동 복귀, 자가 재시작, 하트비트·에러 리포팅 |
| 9 | 출시 기준 통과 | `.claude/rules/operations.md` 체크리스트 전 항목 |

**2번을 모션 없이 먼저 완성합니다.** 모션을 먼저 얹으면 전이 버그와 애니메이션 버그가
뒤섞여 디버깅이 몇 배로 어려워집니다. 상태가 옳다는 것을 확인한 뒤 모션을 덮습니다.

### 변경 통제

- 관련 없는 정리는 feature diff에 섞지 않습니다.
- 기존 사용자 변경을 보존합니다.
- 새 추상화보다 삭제와 재사용을 우선합니다.

### 절차가 아니라 설계로 푸는 규칙

"운영자가 처리하면 된다"로 끝나는 결론을 내지 않습니다.
사람이 할 일이 늘어난다면 그건 자가 복구가 부족하다는 신호입니다.
자세한 기준은 `.claude/rules/operations.md`를 따릅니다.

### 결정 기록

구조, 라이브러리, 공통 규칙, 하드웨어 전제처럼 이후 작업에도 영향을 주는 결정을 내렸다면
`docs/decisions/`에 결정 문서를 추가합니다.

- 기존 규칙을 그대로 따르는 단순 구현은 기록하지 않습니다.
- 결정 문서는 근거와 대안을 짧게 남기는 용도이며 작업 로그로 사용하지 않습니다.

## 검증

주장을 증명할 수 있는 가장 작은 검증을 선택합니다.

### 명령어 선택

- 문서만 변경한 경우: 변경 파일을 확인하고 build는 생략합니다.
- 좁은 컴포넌트/훅 변경: 관련 테스트가 있으면 실행합니다.
- 상태 머신, 매핑 테이블, 스키마 변경: 관련 테스트와 `pnpm lint`를 실행합니다.
- 에셋 추가/변경: `pnpm check:assets`를 실행하고 **예산 수치를 변경 전/후로 보고**합니다.
- 앱 전반 변경: `pnpm lint`, `pnpm typecheck`, `pnpm build`를 실행합니다.

### 성능 검증 — 개발 맥 기준으로 판단하지 않습니다

렌더링은 TV SoC에서 일어납니다. 개발 맥에서 60fps인 것은 실기에서 돈다는 증거가 아닙니다.

- 모션 변경은 **DevTools Performance에 CPU 6x 스로틀**을 걸고 측정합니다.
- 측정 구간(어느 전환인지), 스로틀 배율, 프레임 드랍 수치를 함께 보고합니다.
- 메모리는 **시간축 수치**로 봅니다. heap snapshot을 주기적으로 떠 우상향 추세를 확인합니다.
- 장시간 구동 테스트는 **반드시 스탠바이미2 실물에서** 합니다.

### 근거로 인정하지 않는 것

- "부드럽게 동작합니다", "누수 없어 보입니다" 같은 서술
- 개발 맥에서만 확인한 성능 수치
- `test.skip`, 빈 테스트, 실행하지 않은 테스트

### 보고

최종 보고에는 아래 내용을 포함합니다.

- 무엇을 변경했는지
- 무엇을 검증했는지 (명령어와 수치)
- 검증하지 못한 항목과 이유 — 특히 **실기 확인이 필요한 항목**

명령어가 환경 또는 의존성 문제로 실패하면 blocker와 다음으로 신뢰할 수 있는 근거를 보고합니다.
