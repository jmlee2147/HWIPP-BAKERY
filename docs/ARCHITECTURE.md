# 아키텍처 — 설계 근거

> 이 문서는 **왜 이렇게 결정했는가**를 기록합니다.
> 지켜야 할 규칙은 `.claude/rules/`에, 개별 결정 기록은 `docs/decisions/`에 있습니다.
>
> 기준 문서: Notion `졸스3- 기능명세서` (KIS_01 / User Kiosk), Figma `전시 디자인 공유` (node 1-77703)

---

## 1. 제품

졸업작품전시회에 설치되는 키오스크 체험물. 관람객이 "누구에게 줄 케이크인가"를 문답으로
입력하면 AI가 관계성 데이터를 케이크 레시피(컬러·디자인·맛·레터링)로 변환해 보여주고,
QR로 소장·확산시킨다.

```
시작 → STEP.1 타겟 설정 → STEP.2 데이터 입력 → STEP.3 AI 분석
     → STEP.4 결과 도출 → STEP.5 소장·확산
              └ 수정하기 → STEP.2 (프리셋) → STEP.3 재진행
```

## 2. 구성 (확정)

```
스탠바이미2 webOS 24 브라우저 ──Wi-Fi──▶ Vercel 배포 URL
  └ 렌더 + 터치 전부 자기가 처리            └ API · 결과 저장소
```

| | |
| --- | --- |
| 표시 | LG 스탠바이미2 27LX6 · 세로 회전 · 1440 × 2560 |
| 디자인 캔버스 | Figma 세로 1080 × 1920 (9:16 동일, 정확히 4/3배) |
| 입력 | 터치 |
| 네트워크 | 와이파이 전용 (유선랜 포트 없음) |

전시장에 컴퓨터를 두지 않는다. 결정 근거는 `docs/decisions/001-webos-browser.md`.

## 3. 기술 선택과 근거

| 레이어 | 선택 | 근거 |
| --- | --- | --- |
| 프레임워크 | Next.js 15 (App Router) | AI 호출 Route Handler와 QR 공유 페이지를 한 저장소에서 처리 |
| 언어 | TypeScript (strict) | 문답 스키마 ↔ AI 응답 ↔ 결과 렌더를 한 타입으로 묶음 |
| 스타일 | **Tailwind v3** | webOS 24 = Chromium 108. v4는 Chrome 111+ 요구 (§5) |
| UI 모션 | Motion (`motion`) | `layoutId` 기반 STEP 전환이 이 플로우와 정확히 맞음 |
| 그래픽 모션 | Lottie (dotLottie) | 디자이너 AE 워크플로와 마찰이 적음 |
| 상태 | Zustand 단일 세션 스토어 | 5-STEP 위저드 + 수정하기 재진입을 하나의 상태로 |
| AI | Anthropic SDK / `claude-opus-5` | 구조화 출력으로 결과 카드 스키마 보장 |
| 결과 이미지 | Satori + resvg (서버 렌더) | 폰트·레이아웃이 기기와 무관하게 결정적 |
| 배포·저장소 | Vercel + KV | QR 공유 페이지가 공개 URL을 요구하므로 배포는 어차피 필수 |

### 검토했으나 채택하지 않은 것

- **Vite + React** — AI 호출용 백엔드를 따로 띄워야 함. 관리 포인트가 둘로 늘어난다.
- **GSAP** — 타임라인 제어는 강력하나, React 상태와 물린 전환이 주축이라 Motion이 더 적합.
  복잡한 시퀀스 1~2곳에 한해 국소 도입은 가능.
- **Rive** — Lottie보다 인터랙티브 모션에 강하지만 디자이너 AE 워크플로 기준이면 마찰이 크다.
  STEP.3 믹싱 모션이 사용자 입력에 반응해야 한다면 재검토.
- **로컬 서버(전시장에 컴퓨터)** — 와이파이가 죽으면 똑같이 멈추므로 실익이 거의 없고,
  그 컴퓨터의 무인 운영 문제를 떠안게 된다.

## 4. 설계를 지배하는 세 가지

### 모션이 매우 많다

개별 컴포넌트가 각자 애니메이션을 정의하면 타이밍이 제각각이 되고 전환 중 언마운트가 꼬인다.
전환·연출·피드백 3계층으로 나누고 각각 단일 구현 위치를 강제한다. → `.claude/rules/motion.md`

### 이미지가 매우 많고 해상도가 높다

디코딩 메모리가 픽셀 수에 비례한다. 풀스크린 1장 ≈ 14MB RAM이고 TV SoC는 RAM을 OS와 공유한다.
파일 크기가 아니라 **동시 상주 디코딩 메모리**로 예산을 잡고 빌드에서 강제한다.
→ `.claude/rules/assets.md`

### 실서비스 기준으로 만든다

당일 운영자는 디자이너고 개발자는 현장에 없을 수 있다. 현장에 있는 사람은 디버깅을 할 수 없다.
**절차로 넘기지 말고 설계로 푼다** — 자가 복구, 자가 재시작, 원격 모니터링.
→ `.claude/rules/operations.md`

## 5. 한 번 결론 난 것 (재논의 금지)

| 주제 | 결론 | 근거 |
| --- | --- | --- |
| HDMI로 컴퓨터를 붙여 터치 받기 | **불가** | LG 공식 안내 + 스펙(USB-C 3조가 전부 USB 2.0) → `decisions/001` |
| 반응형 레이아웃 | **불필요** | 캔버스와 패널이 9:16으로 동일. 균일 scale로 끝 |
| 로컬 서버 운영 | **하지 않음** | 와이파이가 죽으면 똑같이 멈춤. 관리 비용만 늘어남 |
| Tailwind v4 | **v3으로 간다** | 아래 참조 |
| 관리자 대시보드 | **만들지 않음** | 아래 참조 |

### Tailwind v4를 쓰지 않는 이유 — 실물 없이 확정됨

LG 공식 문서 기준 **webOS TV 24 = Chromium 108**이다.
Tailwind v4는 `color-mix()` 등에 의존해 **Chrome 111+**를 요구하므로 **이 기기에서 깨진다.**

미지원 엔진에서 v4는 폴백 없이 무너진다. CSS는 대부분 폴리필로 메꿀 수 없어
"일단 쓰고 나중에 대응"이 성립하지 않는다. 추측이 아니라 확정 사실이므로 재검토하지 않는다.

같은 근거로 쓸 수 없는 것: `color-mix()`(111), CSS nesting(112), View Transitions(111),
`text-wrap: balance`(114), Subgrid(117).

반대로 **쓸 수 있는 것이 생각보다 많다**: `:has()`(105), container query(105), `@property`(85),
cascade layers(99), Service Worker, Fullscreen API, Pointer Events, Web Animations API,
그리고 **AVIF(85)**. 초기에 보수적으로 금지했던 항목 중 상당수가 실제로는 사용 가능하다.

### 관리자 대시보드를 만들지 않는 이유

제안된 항목을 하나씩 따졌을 때 근거가 남는 것이 없었다.

| 두려던 것 | 기각 사유 |
| --- | --- |
| 현재 세션 상태 | 운영자가 27" 화면을 직접 보고 있다 |
| 누적 세션 수 | 결과 레코드가 KV에 쌓인다. 전시 후에 세면 된다 |
| 에러 로그 | `/api/*` 실패는 Vercel 로그에 남는다 |
| 에셋 프리로드 상태 | 부팅 화면 진행률로 충분하다 |
| 강제 리셋 | `[처음으로]` + 유휴 타임아웃 + 에러 자동 복귀가 이미 처리한다 |

더 근본적으로, **현장에 있는 사람은 디버깅을 할 수 없다.** 능력이 아니라 역할의 문제다 —
디자이너는 관람객을 응대하러 온 것이지 장비를 감시하러 온 것이 아니다.
관리 화면을 줘도 판단을 요구하는 순간 쓸모가 없어진다.

**관리 화면이 필요하다는 결론은 대개 자가 복구가 부족하다는 신호다.**
감시는 개발자가 원격으로 한다 — 하트비트 + 에러 리포팅 + 폴백 카운터 + 알림.
예외로 `/debug` 한 장만 둔다 (설치 시 1회용).

## 6. 미확정 — 실물 확보 후 판정

구현을 막지는 않는다. 아래 중 **1번만 치명적**이고 나머지는 전부 폴백이 준비되어 있다.

| # | 확인 | 실패 시 |
| --- | --- | --- |
| 1 | **`requestFullscreen()`이 브라우저 UI를 실제로 숨기는가** | 막히면 유일한 B안 전환 사유 |
| 2 | 뷰포트 / `devicePixelRatio` | 1080×1920이면 스케일 자체가 불필요해짐 |
| 3 | Lottie 프레임 유지 | 시퀀스 PNG/WebM으로 대체 |
| 4 | 실기 메모리 여유 | 300MB 예산 조정 |

엔진 버전·서비스워커·AVIF·CSS 기능 지원은 **Chromium 108로 확정**되어 확인이 끝났다.
남은 것은 스펙으로 알 수 없는 것들뿐이다.

확인은 `/debug` 페이지 하나로 한다 — webOS 브라우저에는 개발자도구가 없다.

**1번이 A안의 유일한 치명적 리스크다.** 다만 **Chromium 108은 Fullscreen API를 지원한다.**
남은 불확실성은 API 지원 여부가 아니라 webOS 브라우저 앱이 그 호출에 맞춰 자기 UI를 숨기는지다.
시작 화면의 첫 탭이 사용자 제스처가 되어 전체화면에 진입한다(`.claude/rules/operations.md`).
그 경우 최악의 노출은 **idle 화면에서만 주소창이 보이는** 수준으로 축소된다.

### B안 (폴백)

1번이 막히면 **IR 터치 오버레이 프레임 + 컴퓨터** 구성으로 전환한다.
되살아나는 것: 데스크톱 성능 예산, 유선 이더넷, macOS 무인 운영 설정.
잃는 것: 스탠바이미2의 깔끔한 외형(베젤 10~15mm 추가).

## 7. 그 외 결정 필요

**설계**
- STEP.1 수신자 타입 최종 목록 (명세 "등"으로 열려 있음)
- 케이크 디자인 에셋 variant 개수 → 디코딩 메모리 예산에 직결
- STEP.3 믹싱 모션이 사용자 입력에 반응하는지 (Yes → Rive 재검토)

**운영 준비**
- 전시장 와이파이 조건 — 고정 SSID인가, 캡티브 포털이 있는가, 기기 수 제한이 있는가
- 전시용 단축 도메인 확보 (QR 스캔 성공률 + 리모컨 입력 편의에 직결)
- Vercel 프로젝트·KV 생성, preview/production 네임스페이스 분리
- `/api/analyze` 일일 호출 상한값 — 예상 관람객 수 기준
- 전시 기간·운영 시간 → 장시간 구동 테스트 길이 결정
